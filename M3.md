# M3 natif Rust : intégration directe dans le fork Bun

## Mandat et résultat attendu

Implémenter la chaîne M3 complète avec les propriétaires Rust et les API réelles
du fork Bun. Aphrody consomme cette chaîne pour son app, son site, son showcase
et ses thèmes OS. Ne pas réécrire Aphrody, porter ses algorithmes en TypeScript,
copier les crates Bun dans Aphrody ou ajouter un fournisseur de tokens concurrent.

Le résultat doit relier les sources Google, les tokens Rust, le CSS, le bundler,
les composants, le rendu et les consommateurs avec des contrats vérifiables.
Une exportation JSON ne prouve pas le rendu d'un composant ; un exemple WebView
ne prouve pas l'existence d'un framework natif complet.

Lire d'abord [AGENTS.md](AGENTS.md), [PLAN.md](PLAN.md),
[APHRODY.md](APHRODY.md), [PLAN-FRAMEWORK.md](PLAN-FRAMEWORK.md) et les consignes
du checkout Aphrody sélectionné. Le 2026-10-09, `GOAL.md`, `MEMORY.md` et
`START-HERE.md` sont absents de la racine de ce fork ; ne pas les inventer.
`PLAN.md` indique l'index mémoire installé du projet Bun.

## Intégration Rust → CSS → Bun

Chemin immédiatement réutilisable : générateur Rust canonique → artifact JSON/CSS
validé → plugin M3 existant → Tailwind pour ses directives → `Bun.build` CSS natif.
Un consommateur TS reste un adaptateur de contrat ; il ne calcule pas les couleurs.

Plugin Aphrody : `m3/packages/m3/src/plugin.ts`, options `nativeTheme` et `css`.
Découverte native : `src/native.ts`, `APHRODY_DESIGN_CORPUS` ou plus proche
`var/mirrors/design-sync/tokens.json` ; le seed/variant/contraste doivent correspondre.
Les namespaces `m3:tokens.css` et `m3:theme.css` retournent `loader: 'css'`.
Un callback `css` explicitement demandé garde sa priorité contractuelle.
`m3/packages/m3-bun/src/plugin.ts` utilisait un callback `tsM3Css` implicite qui
court-circuitait la sélection native. Il délègue maintenant `m3Plugin(m3Options)`.
Le lot a 3 tests de build réels réussis, 12 assertions : artifact pet par défaut
et priorité du callback explicite. Cela ne ferme pas le gap Tailwind ci-dessous.

Dans le fork, `packages/bun-plugin-tailwind/src/m3.ts:75`, `seed:false` évite
`m3SchemeCss`/`schemeFromSeed` TS et conserve les imports de presets nécessaires.
L'expansion `@theme`, `@source`, `@apply` appartient au plugin Tailwind ; le loader
CSS Bun seul n'implémente pas ces directives. Préserver les namespaces/imports,
sourcemaps, dépendances CSS, HMR, ordre des plugins et files d'assets.

Écart fermé le 2026-10-09 (fork `92dad165a7c`, Aphrody `0dab9e497b`). Les versions
publiées `0.1.0-aphrody.1` à `.3` ne contenaient pas `holdSchemeImports`/`restoreSchemeImports` :
Aphrody échouait sur `Can't resolve 'm3:theme.css'` (9 échecs sur 18 tests m3-bun
plugin/build). `@tailwindcss/node` 4.3.3 n'offre que `customCssResolver(id, base)` vers
un chemin. Le propriétaire expose donc `TailwindOptions.schemeImport(id, importer)` :
le CSS rendu remplace chaque `@import "<scheme>:…";` inconditionnel avant le compile
(récursif, cycle = erreur, `undefined` garde l'import pour le bundler). Le `@theme inline`
des feuilles Rust atteint ainsi le vrai compiler. `@aphrody/bun-plugin-tailwind@0.1.0-aphrody.4`
est publié. `m3Plugin` lui passe `SHEET_MODULES` → `sheet(kind)`, sans calcul TS.
Preuves : test fork « schemeImport » (Bun.build + core : 14 pass, 2 échecs sourcemap
préexistants du binaire installé `f7a7086b6` sans `.css.map`). Aphrody `m3` et `m3-bun` :
243 pass, 13 skip, 0 fail avec le paquet publié. L'assertion périmée `shape-corner` de
`build.test.ts` venait de l'ancien `tsM3Css` ; elle vérifie maintenant l'absence de `@theme`.
Une feuille `m3:*` importée depuis JS ou par un import conditionnel passe par
`TailwindRoot` du propriétaire (`compileSheet`, Aphrody `c392cea8e3`) : le test m3-bun
correspondant exige 0 log et aucun `@theme`. Avec `tailwind:false` explicite (Aphrody

resets `--x-*: initial` retirés) ; test plugin : 0 log, aucun `@theme`, rôles et alias présents.

Bridge Rust de bundler existant : crate `bun-native-plugin` 0.2.0,

## CSS Rust interne : possibilités et contraintes

`src/css/css_parser.rs` expose `StyleSheet::parse` (2556), `minify` (2349),
`to_css` (2540), avec `ParserOptions`, `MinifyOptions`, `PrinterOptions`.
`src/css/lib.rs` réexporte ces types, couleurs et targets ; `src/css_jsc` relie
`Bun.color` à JSC. Les conversions CSS génériques ne remplacent pas MCU/HCT.

La crate `bun_css` exige nightly/`allocator_api`, des arenas et des types internes.
Le parse exige actuellement `&'static Bump` ; respecter la durée de vie réelle,
les propriétaires AST/symbols/imports et les destructeurs des allocations d'arena.
Sa fermeture native inclut `bun_core`, `bun_hash` et les extern C++ de `bun_highway`.
L'absence de dépendance JSC directe ne prouve pas une crate autonome stable/linkable.
`StyleAttribute::minify` reste un TODO à `css_parser.rs:2806`.
Toute extraction réellement nécessaire se fait dans le propriétaire du fork,
avec tests et qualification de lien ; ne pas recopier son parser dans Aphrody.

## FFI, SDK, WASM et desktop

FFI existante Aphrody : `packages/interop/native` publie `@aphrody/bun`.
`src/index.ts:286` appelle `bun_rs_m3_css`, vérifie l'envelope et libère la CString
avec `bun_rs_free_string`. `crates/ui/bun/src/lib.rs:262` utilise
`sheets::SheetRequest::parse` puis `aphrody_m3_tokens::sheets::render`.
`crates/ui/bun` est un rlib ; le cdylib réel est `crates/interop/ffi` (`aphrody_ffi`).
Le loader contrôle pin/ABI/target ; pas de DLL fictive, contournement ou skip ajouté.
`@aphrody/bun` est cette liaison produit, pas le binaire `@aphrody/bun-runtime`.

Le SDK `packages/bun-runtime-sdk` conserve `yolo_*` et ses règles d'allocation.
`yolo-runtime` a `default=[]` et n'expose pas déjà M3/CSS : étendre le propriétaire
approprié uniquement si le contrat le demande. Pas de seconde couche SDK parallèle.
Définir UTF-8 ptr/len, taille bornée, erreurs, free par l'allocateur d'origine,
panic/unwind, threads, callbacks, annulation et durée de vie de chaque artifact.

`src/wasm` exporte semver, shell parser et markdown pour `wasm32-wasip1-threads`.
Ce n'est pas un moteur browser M3/CSS/render. La présence de `WebAssembly` dans Bun
ne qualifie pas un module WASM M3. Préserver les ABI alloc/free déjà existantes.
Pour du M3 browser, compiler la même implémentation Rust pour la cible réellement
supportée et mesurer son artifact/loader ; ne pas masquer du TS sous le nom WASM.

Hôte desktop réel : `packages/bun-tauri/crates/aphrody-tauri-runtime-cef`, CEF
152.3.0, `CefRuntime`/`CefRuntimeHandle`, Tauri + tauri-winit + GTK4.
Conserver ce runtime canonique ; pas de wry/tao/system WebView de remplacement.
`bun-webview-core/src/backend/mod.rs` implémente actuellement GTK4 et Mock ; ses
labels WebView2/WKWebView/CEF ne prouvent pas ces backends. `bun-webos/examples/
m3-native-app` utilise HTML/TS + Bun.serve/WebView, pas un rendu natif Rust M3 complet.
Les pages distantes n'obtiennent aucun accès Bun/host privilégié implicite.
