---
title: bun plugin
description: Cold parts of Bun shipped as separate executables, fetched on first use.
---

Some commands of Bun run in a separate executable, a plugin, so the `bun` executable stays small and starts fast. `bun uv`, `uv`, `uvx` and Python compilation run the `uv` plugin, `bun-uv`; `bun vpn` runs `bun-vpn`; `bun ssh` and `bun rsync --native` run `bun-ssh`; `bun docker` runs `bun-docker`; `bun just` runs `bun-just`; `bun winmd` runs `bun-winmd`. The `build-essential` plugin (`bun-build-essential`) is built and released with the others but not yet dispatched by `bun`.

A plugin is looked up, in order:

1. next to the `bun` executable (`bun-uv`, `bun-uv.exe`), where a build of the checkout puts it;
2. in `$BUN_PLUGINS_DIR`, or `$BUN_INSTALL/plugins` (default `~/.bun/plugins`), under `<name>/<version>/`.

When it is missing, the first command that needs it downloads it from the GitHub release of the running Bun (`bun-v<version>`, or `aphrody-v<version>` for a build with a version tag, then `main-runtime-<revision>`), checks it against the release's `SHA256SUMS.txt`, and installs it in the plugin directory. Plugins of an older Bun are removed when the new one is installed, so `bun upgrade` needs no extra step.

```sh
bun plugin list            # every plugin and where it is
bun plugin install uv      # download it now
bun plugin remove uv       # delete the downloaded copy
```

The plugin receives the command's arguments, standard input and output, environment and working directory, and its exit status is the command's.

| Variable                           | Effect                                                                               |
| ---------------------------------- | ------------------------------------------------------------------------------------ |
| `BUN_PLUGINS_DIR`                  | Plugin directory; when set, it is the only place looked at                           |
| `BUN_PLUGIN_RELEASE_URL`           | Directory URL holding the assets and `SHA256SUMS.txt`, instead of the GitHub release |
| `BUN_PLUGIN_NO_DOWNLOAD=1`         | Fail instead of downloading a missing plugin                                         |
| `APHRODY_BUN_REPO`, `GITHUB_TOKEN` | Repository and token used for the release, as for `bun upgrade`                      |

Release assets are named `bun-<name>-<os>-<arch>[-musl][.exe]`, for example `bun-uv-linux-x64` or `bun-uv-windows-x64.exe`.

## Building a plugin from source

Each plugin is its own repository, mounted in the Bun checkout as an optional submodule under `plugins/` (`update = none`, so a plain clone or `git submodule update` leaves it out):

| Plugin   | Repository                                                            | Bundles                                                       |
| -------- | --------------------------------------------------------------------- | ------------------------------------------------------------- |
| `uv`     | [aphrody-labs/bun-uv](https://github.com/aphrody-labs/bun-uv)         | uv 0.12.24 (`vendor/uv`, aphrody-labs/uv `bun-0.12.24`)       |
| `vpn`    | [aphrody-labs/bun-vpn](https://github.com/aphrody-labs/bun-vpn)       | `bun_vpn`, Mullvad (`vendor/mullvad`, GPL-3.0-or-later)       |
| `ssh`    | [aphrody-labs/bun-ssh](https://github.com/aphrody-labs/bun-ssh)       | `bun_ssh`, patched `russh-sftp`                               |
| `docker` | [aphrody-labs/bun-docker](https://github.com/aphrody-labs/bun-docker) | `bun_docker`; needs `plugins/ssh` mounted too                 |
| `just`   | [aphrody-labs/bun-just](https://github.com/aphrody-labs/bun-just)     | `bun_just` (`vendor/just`, aphrody-labs/just `bun`)           |
| `winmd`  | [aphrody-labs/bun-winmd](https://github.com/aphrody-labs/bun-winmd)   | windows-bindgen; uses the checkout's `vendor/find-msvc-tools` |

```sh
git submodule update --init --checkout --recursive plugins/uv   # or: plugins (all of them)
bun bd --target=plugins                                         # bun-<name> next to bun
```

`bun bd` builds only the plugins whose submodule is checked out. Each plugin is a Cargo workspace of its own, with its own `Cargo.lock`, that path-depends on crates of the checkout.
