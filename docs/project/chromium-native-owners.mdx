# Chromium family and native Bun owners

## Read-only profile metadata — source contract, 2026-10-13

`bun:chromium.profiles.discover()` discovers Chrome/Chromium metadata on demand.
An explicit `userDataDirs` list selects fixture or owner directories. `isDefault`
means the literal `Default` directory; `isLastUsed` reflects `Local State`, which
may select another profile. No profile is copied, unlocked or opened for writing.

`profiles.readBookmarks(absoluteFile, { site, includeSubdomains })` reads one
selected JSON file. Site filtering accepts HTTP(S), normalizes case and IDNA,
and matches the exact hostname unless dot-delimited subdomains are requested.
Metadata reads are bounded to 8 MiB; bookmark traversal is bounded to 100000
nodes and 64 folder levels. Errors do not include raw JSON values.

`profiles.capabilities()` keeps encrypted-store export separate from APIs of an
already connected browser. Direct cookies/password-store export is unavailable;
site cookies and live tab metadata require their browser-native owners. Chromium
Windows app-bound encryption validates the calling application as well as its
user, according to `chrome/browser/os_crypt/README.md`; DPAPI alone does not
establish access to those values. Branded Chrome also rejects remote-debugging
switches with its normal user-data directory. Discovery does not change either
policy or launch a browser against that directory. CEF/WebView2 persistence
remains in the destination engine's own store.

The corresponding tests use synthetic `Local State` and `Bookmarks` files.
Source contracts do not establish qualification of a live protected profile or
native Windows credential handling.

Owner directive, 2026-10-11: support Chromium-family browsers across qualified
platforms and converge browser JavaScript on Bun's JavaScriptCore. Reuse native
Bun owners for Python, dependencies, toolchains and browser lifecycle. The
delivery product remains one Bun CLI, runtime, FFI, MCP registry and agent
plugin. This inventory describes actual source and installed help, not a
qualified Chromium build or replacement of Chromium's V8 internals.

## System packages: implemented and missing

`src/install/system/mod.rs::source_for` returns APK, winget and
`deb::apt::Deb` providers. `cli.rs::run` dispatches `apt` and `deb` to the
existing Debian owner. Pacman still has no provider and returns an explicit
unsupported error. Candidate native CLI execution requires its own receipt.

Winget resolves its index/manifests directly, validates hashes, selects the
host installer and refuses unsupported elevation. APK owns repository/rootfs
transactions and script policy. Retain those owners and exact lock provenance.
The Linux adapter in `src/install/system/deb/apt.rs` delegates signature checks,
dependency solving and transactions to existing APT/dpkg executables. It keeps
authentication checks enabled, records exact package metadata and requires an
explicit initialized Debian root for transactions. Its separate `apt plan`
command handles local metadata only and does not verify Release signatures.
Qualify candidate CLI dispatch, root isolation, offline/elevation behavior and
real signed-repository transactions before declaring delivery. Factory bootstrap
may use its declared apt-get path and must report that execution explicitly.

## Python and depot_tools compatibility

Reuse embedded UV for interpreter/project acquisition and Bun's CPython host
for Python execution only where its native contract matches the invoked tool.
depot_tools and Chromium tooling can inspect `sys.executable`, launch child
Python interpreters and depend on filesystem/environment/exit semantics.
An in-process `Python.eval` call does not replace those executable contracts.

Preserve `BUN_PYTHON_HOST_LIBRARY`, `BUN_PYTHON_LIBPYTHON`, explicit
`BUN_PYTHON_EXECUTABLE`/virtual-environment selection, host ABI and interpreter
revision. Keep protected auth/caches outside source. The dedicated toolchain
integration lot owns depot_tools pins and qualification; this document creates
no alternate launcher, global install or substitute dependency manager.

## Chromium and JSC are separate qualification decisions

The current native detection order is explicit `backend.path`,
`BUN_CHROME_PATH`, PATH, platform application locations and historical browser
caches. `BUN_WEBVIEW_HOST` selects the existing optional platform host. Browser
reuse is process-owned; independently isolated profiles/contexts require
qualification, not inference from multiple JavaScript wrapper instances.

Retain Chromium-family acquisition/CDP compatibility while implementing a
separate remote-page realm in Bun JSC. The realm must not expose Bun, Node,
Python, FFI, filesystem, process, environment or system installers to remote
content. Qualify DOM/GC handles, modules, promises/microtasks, timers, workers,
interrupts, exceptions and teardown with identical fixtures before retiring the
legacy page V8 provider. Supporting CDP clients is not replacement of Chromium
or CEF's internal JavaScript engine. A Chromium-internals JSC replacement needs
its own explicit embedding, build and behavior proof.

The feature inventory hashes `ChromeProcess.rs` and the page JavaScript build
script alongside workspace manifests. The page build's cross-target snapshot
path now rejects a missing target `cross-mksnapshot` instead of embedding a
host architecture snapshot. Cross-target execution still requires a matching
snapshot producer and actual target fixture receipt before packaging or activation.
The native Bun/JSC candidate and existing Chromium CDP process require their
own source-matched runtime receipts.
