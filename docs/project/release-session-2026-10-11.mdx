## Pipeline and deployment rules

Build and publication work must be dispatched through each product's owner workflow. Independent targets may run concurrently only when they have separate factory locks, sufficient measured capacity and disjoint source/output ownership. Jobs that share a host-wide heavy-build lock remain serialized.

Current asynchronous support is partial. Aphrody Infra's factory accepts `run --detach --job <stable-id>` and exposes durable `status --job`; an ambiguous SSH result requires reconciliation rather than blind resubmission. Its `--detach --install` path still waits for the client-side install. Bun's [`scripts/aphrody/monorepo-delivery.ts`](../../scripts/aphrody/monorepo-delivery.ts) supports detached profile-qualified build/release jobs and detached consumer installs with stable input-derived IDs, durable status/log/report/step receipts and `--status --job <id>`. Repeated submission of the same ID and inputs does not relaunch it; input collisions fail. An exclusive worker lock also rejects duplicate manual workers, and source drift records a durable failed receipt. The focused delivery suite passes 35 tests and 168 assertions through the existing debug runtime; no native rebuild was performed for these TypeScript-only changes. Detached install rechecks its qualified report and target manifest hashes, then uses a per-target lock; an interrupted install can require manual lock reconciliation and is never replayed automatically. Its scheduler runs dependency-ready steps concurrently only with a fresh qualified factory-capacity profile; without one, attached `--apply` awaits steps sequentially. The [GitHub delivery workflow](../../.github/workflows/aphrody-monorepo-delivery.yml) now derives a live CPU/RAM/disk profile within its constrained factory container and schedules dependency-ready steps through the same heavy-build lock; it exposes inventory, build and release-check. Its durable reports are uploaded after success or failure. The implementation and shell syntax are qualified locally; remote CI execution remains a separate gate. NPM, Cargo and runtime publishers still serialize their dependency-ordered mutations. There is no shared asynchronous update/deploy coordinator or end-to-end receipt spanning all owners yet.

The safe next step is a durable submit/status/receipt interface for the whole release DAG, reusing the existing Infra factory and capacity scheduler. It must preserve dependency waves, immutable source and input hashes, package/version idempotency, the canonical heavy lock and deployment plan/health/rollback gates. Independent builds, package staging and read-only registry checks can run concurrently within observed CPU, RAM and disk limits; mutations against the same version or production host remain serialized. A nonblocking dispatcher must return a stable job identity and durable state, keep logs and receipts, reconcile uncertain submissions and never mark a publish/deploy successful before read-back and health checks pass.

Production apply requires a current deployment plan, explicit target and revision, health validation, and a tested rollback path. Active services are not classified as unused from process age or idle CPU alone. This session did not issue a production apply on VPS, DBFR, Omar or the local PC.
